Claude Code とは何か

名前に Code とあるが、コードを書くためだけの道具ではない。「AIに手足と権限をつけて、自分のPCの上でループを回す仕組み」——それが実体だと分かるまでに、ずいぶん遠回りをした。この第1部では、そこに至るまでに引っかかった順序で書いていく。

学習まとめ 第1部 ／ 2026-08
01

チャットとの違いは「答えるか、やるか」

ブラウザで使うAIに質問すると、答えが返ってくる。そこから先——ファイルを開く、コマンドを打つ、結果を確認する——は人間の仕事だった。

Claude Code は、その先をAI自身がやる。ファイルの読み書き、コマンドの実行、gitの操作を、自分で判断しながら順番にこなしていく。チャットAIが「答えを返すだけ」なのに対して、こちらは「実際に手を動かす」。

質問に答える存在から、代わりに作業する存在へ。

この違いは体験してみると分かりやすい。チャットで「このコマンドを打ってください」と言われてターミナルに貼り付ける、あの手作業が丸ごと消える。

コード専用ではない

ここは名前に騙されやすいところだった。実際には、ファイル操作・データ整形・レポート作成・ドキュメント生成といった業務もこなせる。エクセルの整形、議事録の要約、データ分析の補助のように、コードを書かない仕事でも使える。

フォルダに CSV を置いて「読んで集計して」と頼めば、それで成立する。プログラミングではなく、フォルダの中身をAIに任せるという使い方になる。

02

どう動いているのか — agentic ループ

中で何が起きているかを知ると、設定ファイルの意味が一気に分かる。やっていることは「読む → 考える → ツールを使う → 結果を見る → 繰り返す」のループで、6段階に整理されている。

  1. ユーザーがターミナルにメッセージを入力する
  2. システムプロンプトを組み立てる — 現在の日付、gitの状態、CLAUDE.md、使えるツール一覧
  3. APIを呼び出す → モデルが「このツールを使いたい」と返す
  4. 権限チェック — 自動承認 / 確認を求める / ブロック のどれかを決める
  5. ツールを実行し、結果（ファイルの中身、コマンドの出力）を会話に追加する
  6. 結果を受け取ったモデルが、次のツールを呼ぶか、最終的な返答をする。ツール呼び出しが無くなるまで繰り返す

2番と4番が、後で出てくる設定ファイルの働く場所になる。何を読ませるかが2番、何を許すかが4番。この2箇所しかない、と分かってしまえば設定の話は難しくない。

ローカルで完結している

このループは手元のターミナルのプロセスの中だけで回る。WebFetch や WebSearch、MCPサーバーのように明示的に外部を呼ぶツールを使わない限り、ファイルもシェルも認証情報もマシンの外には出ない。

だから業務データを置いたフォルダで動かせる。ブラウザにファイルをアップロードする使い方とは、ここが決定的に違う。

03

どこまでが Claude Code なのか

学習していて一番混乱したのがここだった。「Claude Code」「.claude」「CLAUDE.md」が、どれも似た名前で別のものを指している。3階建てで考えると整理できた。

① Claude（モデル） 判断する部分。頭脳。Claude Code 専用ではなく、チャットで動いているものと同じ種類
② Claude Code ツール本体。上のループを回し、ツールを実行し、権限をチェックする仕組み
③ .claude/ 設定ファイル群。ループの振る舞いを外から調整する。自分が書く場所

面白いのは、② が「AI」ではないことだ。②はAIに手足をつけて回す機構であって、賢さそのものは①が担っている。この分離が分かると、「設定を変えてもモデルは賢くならない」という当たり前のことが腑に落ちる。

入口は1つではない

Claude Code は2025年2月に限定リサーチプレビューとして公開され、同年5月に一般提供が始まった。登場当初はターミナル中心だったが、2026年時点ではターミナル、IDE、デスクトップアプリ、ブラウザから使える。Remote Control を使えば、手元のマシンで動いているセッションをスマートフォンから続きから操作することもできる。

つまり「Claude Code＝黒い画面」ではなく、同じ仕組みへの入口が複数ある状態になっている。

04

なぜ設定ファイルが要るのか — モデルの持病

ここが、この第1部で一番書きたかったところ。設定ファイルの作法は、ほぼ全部が①の弱点への対処だった。

Lost in the Middle

スタンフォード大学 Liu らの論文「Lost in the Middle: How Language Models Use Long Contexts」（2023年公開、2024年TACL掲載）で報告された現象。実験の作りが分かりやすい。20個の文書をコンテキストに入れ、正解が書いてある文書の位置だけを変えて、同じ質問に答えさせた。

結果は綺麗なU字カーブになった。正解が先頭または末尾にあるときは精度が高く、真ん中にあると大きく落ちる。位置を変えただけで精度が30%以上落ちたケースもあった。さらに、正解を真ん中に置いた場合、文書を一切与えずに記憶だけで答えさせたときより精度が下がることさえあった。

情報を渡したのに、渡さないより悪くなる。

この偏りは設定ミスではなく、Transformer の構造に由来する。ひとつは causal mask で、各トークンは自分より前しか参照できないため、先頭付近のトークンが後続すべてから参照されて相対的に重みを集める。もうひとつは多くのモデルが採用する位置エンコーディング RoPE で、距離が離れるほど注意が減衰しやすい。

原因が構造側にあるため、書き方の工夫だけでは根本解決しない。2026年時点、コンテキストウィンドウが数十万トークン規模まで広がっても、根本的には解消されていないとされる。

ただし断定は避けたい。「コンテキストが長い＝必ず起きる」わけではなく、普遍性や重大性はモデルやタスクによって変わるという慎重な見方もある。設計の前提として意識しておく、くらいの温度が適切だと思う。

だから設定が要る、という因果

この持病を知ってから設定の作法を見返すと、全部が同じ方向を向いていた。

設定の作法（③）何のためか（①への対処）
CLAUDE.md は200行以内長いほど中盤が読み飛ばされる
段階的開示（必要な時だけ読む）使わない情報を載せない＝中盤を作らない
条件付きで読み込むルール同上
サブエージェントに委譲し要約だけ返す中盤を親のコンテキストに作らない

②の側にも受け皿がある。作業が一区切りついたら会話履歴をクリアするのが最も単純で効果的な方法で、Claude Code には clear コマンドがある。また /context コマンドで、いま何がコンテキストを占めているかの内訳を見られる。有効にしたまま使っていないMCPサーバーが、知らないうちに圧迫していることがあるという。

皮肉な話として。ルールファイルやMCPサーバーは、会話を始める前からコンテキストを圧迫する。ツール定義とルールだけで数万トークンを使ってしまうと、肝心のファイルを読み込ませた瞬間に「中間」が生まれる。ハーネスを整えすぎると、それ自体が Lost in the Middle を招く。ここは自分でも意外だった。
05

.claude の中身

以上を踏まえて、③の中身を見ていく。ドットで始まるので Finder では見えない（⌘ ⇧ . で表示切り替え）。

プロジェクト/
  CLAUDE.md            ← 毎回読まれる指示書
  .claude/
    settings.json      ← 権限。共有する
    settings.local.json← 権限。個人用、Git除外
    rules/             ← 領域別のルール
    skills/            ← 繰り返す手順
    agents/            ← 別コンテキストの専門家

~/.claude/               ← 全プロジェクト共通（自分の好み）

役割は大きく2つに割れる。お願いを日本語で書くもの（CLAUDE.md・rules・skills）と、できることを機械的に決めるもの（settings.json）。

ファイル書くこと効き方
CLAUDE.mdプロジェクトの前提・方針・やらないことお願い
rules/領域ごとの細かい規約お願い
skills/繰り返す作業の手順お願い
agents/役割特化の分身への指示お願い
settings.jsonツール使用の許可・禁止強制

この「お願い / 強制」の線引きが実務では効く。文章で頼んだルールは破られることがあるが、deny に書いた禁止はループの4番で機械的に弾かれる。取り返しのつかない操作は、頼むのではなく禁止する。

{
  "permissions": {
    "deny": ["Write(./data/**)", "Bash(rm:*)"],
    "ask":  ["Bash(git push:*)"]
  }
}

元データのフォルダへの書き込みを禁止しておけば、うっかり上書きされる事故が仕組みで防げる。読むのは許可されたままなので、集計はできる。

06

学んだことを一行で

その場のプロンプトで直すのをやめて、次も効く場所に書く。

Claude Code の設定ファイルが何十種類あろうと、言っていることはこれに尽きる。①には構造的な弱点があり、②がそれを扱う道具を用意していて、③で自分が設計する。三層はそういう関係になっていた。

そして、AIに任せる範囲と、機械が決定的に守る範囲の境界を自分の手で引くこと。これは Claude Code に限らず、AIエージェント全般に効く考え方だと思う。次の第2部以降で読む記事も、結局は同じ問題を別の角度から扱っていた。
