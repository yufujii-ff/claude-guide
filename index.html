Claude Code / harness engineering

プロンプトを磨くより、
環境を整えるほうが効く。

Claude Code には、AIの振る舞いを「設定ファイル」として設計する仕組みが5つある。それを層として積み上げるのがハーネスエンジニアリング。このページは、その5層と応用トピックを噛み砕いた自習メモ。

↑ 下から積む。下の層ほど「強制力」が強く、上の層ほど「お願い」に近い。

00 / 前提

なぜ「環境側」を整える必要があるのか

ハーネス（harness）は馬具のこと。手綱や鞍を整えて、馬を意図した方向に走らせる、というたとえです。HashiCorp共同創業者の Mitchell Hashimoto が2026年2月に提唱し、OpenAI・Anthropic・Martin Fowler がそれぞれ記事を出したことで一気に広まりました。

核になっている考え方はシンプルです。エージェントがミスをしたら、そのつど注意するのではなく、二度と同じミスが起きないよう環境側を直す。

理由：LLMは毎回「初めまして」だから

LLMの正体は、トークン列を受け取って次のトークンの確率分布を返す、状態を持たない関数です。推論のあいだ重みは一切変わらないし、内部に記憶の置き場もありません。会話が続いているように見えるのは、アプリ側が毎回それまでの履歴をまるごとプロンプトに詰め直して送っているからです。

つまりAIにとっては、プロジェクトのルールも、昨日の失敗も、ディレクトリ構成も、毎回外から入れ直さないと存在しないのと同じ。この「入れ直す仕組み」を丸ごと設計するのがハーネスエンジニアリングです。

呼び名対象問い
プロンプトエンジニアリングモデルへの入力テキスト何を聞くか
コンテキストエンジニアリングモデルに渡す情報全体何を見せるか
ハーネスエンジニアリングモデルの外側の実行環境どう動かすか

後ろほど範囲が広く、コンテキストエンジニアリングはハーネスの一部にあたります。

ここだけ覚える

プロンプトを工夫して直すのは、その場かぎりの対処。設定ファイルに落とすと、次のセッションでも効く。

01 / .claude の中身

5つの層を一枚ずつ見ていく

Claude Code のハーネスは、次の5つのファイル群でできています。どれか1つだけでも効果はありますが、上から順に足していくと役割がきれいに分かれます。

LAYER 1 CLAUDE.md ガイド（お願い）
CLAUDE.md（リポジトリのルート）

Claude Code が最初に読む指示書。プロジェクトの目的、ディレクトリ構成、技術スタック、守ってほしいルールを書きます。「憲法」であって「百科事典」ではない、という線引きが大事です。

書くとよいこと

  • このリポジトリは何のためにあるか（1〜2行）
  • どのディレクトリに何を置くか
  • 技術ルール（例：Pythonは uv run で実行、バージョンは固定）
  • セキュリティルール（例：APIキーを直書きしない、破壊的なgitコマンドは確認を取る）

いちばん効くのは「やらないこと」を書くこと

LLMは放っておくとファイルを整理したり、ドキュメントを足したり、「改善」と称して余計なことをします。やらないこと の節を作って境界線を引いておくだけで、これが目に見えて減ります。

「LLMは否定形が苦手」とよく言われますが、ここでの否定は推論の抑制ではなく行動範囲の定義なので別物です。

個人設定は import で分ける

CLAUDE.md はgit管理されるので、自分好みの設定を直接書き込むとチームに混ざってしまいます。末尾に1行だけ足す方式が便利です。

# CLAUDE.md の末尾
@my-preferences.md

my-preferences.md は .gitignore に入れておく。参照先のファイルが無い場合は単に無視されるので、まだ作っていないメンバーにも影響しません。

読み込みの優先順位

組織の管理設定 → ~/.claude/CLAUDE.md（ユーザー共通） → 親ディレクトリ → カレントディレクトリ、の順で、あとに読まれたものが強い。全プロジェクト共通の個人設定は ~/.claude/CLAUDE.md へ。サブディレクトリに置いた CLAUDE.md は、その中のファイルを開いたときに自動で読まれます。

LAYER 2 Rules ガイド（お願い）
.claude/rules/*.md

.claude/rules/ に Markdown を置くと自動で読まれます。CLAUDE.md に全部書くと膨らむルールを、領域ごとに切り出すための層です。

常時読むか、必要になったら読むか

条件読み込みコンテキスト消費
globs なしセッション開始時に常時ロード常時
globs あり該当ファイルを読んだ時点で遅延ロード条件付き
 
---
description: API層のコーディングルール
globs: "src/api/**/*.ts"
---
# src/api/ 配下のTSを読んだときだけ効く

ルールが増えてきたら globs で条件付きにするのが節約のコツ。

つまずきポイント

公式ドキュメントには paths と書かれていますが、YAML配列がうまくパースされない不具合が報告されています。globs は未ドキュメントながら確実に動くため、現時点ではこちらが安全という報告があります（変わる可能性あり、公式の最新を確認）。

用途の例：タスク管理のカンバン運用ルール、出力ファイルの命名規則やディレクトリ構成など。「このケースではCSVも出す」「ファイル名は YYYYMMDD_名前.md」といった判断を、毎回言わなくてもやってくれるようになります。

LAYER 3 Skills ガイド（お願い）
.claude/skills/<名前>/SKILL.md

/コマンド名 で呼び出せるワークフロー定義。SKILL.md に手順を書いておくだけで、複雑な段取りを一発で走らせられます。description を書いておくと、明示的に呼ばなくても文脈に合えば Claude 側から提案してくれます。

設計の勘所：LLMの仕事とスクリプトの仕事を分ける

ある実践例では、最初 RSS の取得・パースまで LLM にやらせていました。取得元が増えるにつれてトークンも時間も膨らむ。RSSのパースは決定的な処理なので、LLMを通す意味がありません。

# before — 全部LLM
LLM → RSS取得 → パース → フィルタ → 翻訳 → まとめ → 保存

# after — 分業
Python → RSS取得 → パース → JSON出力
LLM    → 翻訳 → 分類 → まとめ → 保存

この分業だけで、トークン消費が約1/6、処理時間が約1/3になったと報告されています。判断と生成はLLM、ループ・集計・ファイル操作はスクリプト。これが基本線です。

環境構築をゼロにする書き方

スキルからPythonを呼ぶときは uv run --with 'パッケージ==版' python3 script.py のインライン実行が便利。uvさえ入っていれば仮想環境もpip installも要りません。バージョンを固定しておけば、予期しない破壊的変更やサプライチェーン攻撃のリスクも下げられます。

LAYER 4 Agents ガイド（お願い）
.claude/agents/*.md

@名前 で呼ぶ、役割特化のサブエージェント。メインのClaude Codeとは別のコンテキストで動くのがポイントです。

たとえば数百ファイルのメモを横断検索する場合、メインでやるとコンテキストウィンドウが埋まってしまいます。エージェントに任せれば、返ってくるのは要約だけ。「〜について何かあったっけ？」のような曖昧な問いを投げる窓口として置いておくと便利です。

使いどころの判断

「大量に読むが、必要なのは結論だけ」なタスクはエージェント向き。逆に、メインの文脈を保ちながら細かくやりとりしたいタスクは向きません。

LAYER 5 Settings ゲート（強制）
.claude/settings.json

ツールの使用権限を制御する層。ここだけは「お願い」ではなく効くので、ハーネスの安全装置にあたります。

{
  "permissions": {
    "allow": [
      "Bash(gh issue *)",
      "Bash(uv run*python3 .claude/skills/*)",
      "WebSearch", "WebFetch", "Write"
    ],
    "deny": [
      "Bash(gh repo delete*)",
      "Bash(gh repo archive*)",
      "Bash(gh pr close*)"
    ]
  }
}

設計の方針

  • allow は業務に必要な範囲で広く。毎回確認が出ると作業のリズムが崩れます
  • deny は破壊的操作を名指しで。リポジトリ削除、アーカイブ、PRの強制クローズなど
  • 共有したい許可は settings.json、URL固定のcurlなどローカル専用は settings.local.json
パイプの落とし穴

パイプ（|）を含むコマンドは各サブコマンドが個別に権限評価されますが、jq式の中の | まで区切りとして誤認されるなど、allowパターンだけでは解決しきれない場合があります。後処理が必要なら、パイプなしで実行してJSON出力をそのままLLMにパースさせるほうが確実です。

最初から完璧な権限設定は無理です。「実行してみて確認が出る → 許可を足す」を回して、だんだん快適に寄せていくのが現実的。

番外 Hooks ゲート（動的）
settings.json 内で定義

イベント駆動の自動処理。CLAUDE.md や Rules が「お願い」なのに対し、Hooks は決定的に走るのが違いです。

  • PreToolUse — 破壊的コマンドのブロック、禁止パターンのチェック
  • PostToolUse — 書き込み後の自動フォーマット、リント
  • UserPromptSubmit — 入力の検証、プロンプトインジェクション検出
  • セッション開始／終了時の処理、タスク完了通知

ただし、急いで入れなくていい

ブロック用途だけなら settings.json の deny で足りるケースが多い。deny は静的なパターンマッチで即座に止めます。Hooks が本当に必要になるのは、パターンでは表せない動的な判断——「変更対象ファイルの中身を見て検証する」「外部サービスに問い合わせて判断する」——が要るときです。

さらに Hooks の prompt / agent ハンドラはツール実行のたびにLLM呼び出しが走るので、トークンのオーバーヘッドも無視できません。deny で足りるうちは deny で。

02 / 応用

スキルをちゃんと作る

Skills は Anthropic が2025年10月に導入し、同年12月にオープンスタンダードとして公開。2026年3月時点で OpenAI Codex、Gemini CLI、GitHub Copilot など30以上のプラットフォームが採用しています。フォルダ構成は次のとおり。

your-skill-name/
├── SKILL.md      # 必須 — メインの指示
├── scripts/      # 任意 — 実行コード
├── references/   # 任意 — 必要な時だけ読む資料
└── assets/       # 任意 — テンプレ、フォント等

設計の核：段階的開示（Progressive Disclosure）

全部を最初から読ませない。3段階の遅延読み込みで、必要な情報だけを必要なときに載せます。

層中身読み込むタイミング
Level 1name + description（約100トークン）常にシステムプロンプトへ
Level 2SKILL.md 本文（5,000トークン未満推奨）スキルが起動したとき
Level 3scripts / references / assets参照されたときだけ

Anthropic はこの設計を「コンテキストウィンドウは公共財」と表現しています。自分のスキルは、他のスキルやシステムプロンプトと同じ場所を分け合っている、という感覚です。

MCPとの違い

MCPが「手足」（ツール・接続）を、Skillsが「頭の中の知識」（手順・作法）を担います。公式ガイドのたとえでは、MCPが厨房の設備で、Skillsがレシピ。

Anthropic公式の skill-creator から学べること

skill-creator は「スキルを作るためのスキル」。作成→テスト→レビュー→改善のサイクルを回してくれる、いわばスキルのCI/CDです。構造そのものが設計パターンの見本になっています。

① SKILL.md は指揮者に徹する

約480行の SKILL.md は、実は自分では専門処理をしません。採点は agents/grader.md、A/B比較は agents/comparator.md、分析は agents/analyzer.md に投げるだけ。全部1ファイルに書けば1000行を超えますが、分けておけば評価フェーズでは採点役の指示だけがコンテキストに載る。段階的開示をスキルの内部設計にまで持ち込んでいる形です。

② 決定的な処理はスクリプトへ追い出す

公式のベストプラクティスも、コードは決定的だが言語の解釈はそうではない、という趣旨を述べています。並列実行、多段の集計、ZIPパッケージング——このあたりはLLMの苦手分野なのでスクリプトの担当。

③ スキーマ契約を先に決める

LLMの出力はフォーマットがブレます。skill-creator は7種類のJSONスキーマを references/schemas.md に定義し、SKILL.md からは「このスキーマに従え」と参照するだけにしています。フィールド名を1つ間違えるとビューアが空表示になる、という注意書きまで明記されている。LLMとスクリプトを繋ぐなら、この契約書は必須です。

④ 「なぜ」を書く（Why-driven）

ALWAYS / NEVER を大文字で並べたくなったら黄信号、というのが skill-creator の立場。代わりに理由を説明すると、未知のケースにも対応できるようになります。

従来型推奨
送信前に必ず検証すること検証しておくとAPIエラーを防げる。エラーはトークンを無駄にし、ユーザーを困らせる
フォーマット手順を飛ばすな形式を揃えておかないと、ビューアが結果を読めなくなる

ただし本当に危険な箇所——スキーマのフィールド名一致、セキュリティ——は明示的な禁止で書く。両側が崖の細い橋では厳格に、開けた野原では理由で。

⑤ description がすべての生命線

常時システムプロンプトに載るのは name と description だけ。本文はトリガー後に初めて読まれます。つまり description が悪ければ、そのスキルは永遠に呼ばれない。skill-creator は description の最適化だけのために専用スクリプトを3つ用意し、train/test分割と過学習防止まで組み込んでいます。

現状のClaudeはスキルを使わなすぎる傾向がある、と skill-creator 自身が指摘しており、descriptionは少し「押し強め」に書くことが推奨されています。「ダッシュボードの作り方」だけでなく、「ダッシュボード、データ可視化、社内指標などの話が出たら必ずこのスキルを使うこと」のように、起動すべき文脈を列挙する書き方です。

⑥ 人のレビューはチャットの外へ出す

skill-creator はローカルHTMLのダッシュボードを生成して、ブラウザ上でフィードバックを集めます。大量のテスト結果や複数バージョンの見比べは、テキストチャットでは限界があるからです。集めた意見は構造化ファイルに落として、次の反復に反映する。

⑦ 環境ごとのフォールバックを書いておく

サブエージェントの並列実行やブラウザビューアが使えない環境もあります。skill-creator は環境別に「使えない機能→代替手段」を明記しています。大事なのは、コアの流れ（作る→試す→見る→直す）は環境が変わっても同じで、変わるのは各ステップの実行方法だけ、という設計です。

03 / 応用

複数の処理をどうまとめるか

スキルが増えてくると、次は「組み合わせ方」の問題になります。大きく2つの型があります。

Sub-agent型

1つの親スキルが、複数のサブエージェントを生成して並列に走らせる。skill-creator がこれ。

同じ対象を、複数の視点から同時に評価したいときに向く。

Skill Chain型

独立したスキルを数珠つなぎにしてパイプラインを組む。各スキルが自分の SKILL.md / scripts / references を持ち、単体でも使える。

処理に明確な順番があり、フェーズごとに責務が違うときに向く。

# Skill Chain型の例（MLベンチマーク）
agentic-bench
  ↓
model-researcher   # 調査・VRAM推定
  ↓
gpu-runner         # 推論実行
  ↓
eval-reporter      # レポート生成
設計軸Sub-agent型Skill Chain型
実行モデル1スキル内でサブエージェント生成独立スキルの直列連結
コンテキスト親の文脈を継承各スキルが自分の領域だけ持つ
処理フロー並列直列（順序のあるフェーズ）
単体利用サブエージェントは単体では使えない各スキルが独立して使える
references/スキーマ定義（契約書）ドメイン知識（先輩のカンペ）
スクリプト必須コンポーネントあれば便利なオプション
拡張の仕方agents/ や scripts/ を足すreferences/ を1ファイル足す

この2つは排他的ではありません。Skill Chain の各フェーズの中で Sub-agent を並列に生成する、といった融合も普通にありえます。また「Sub-agent型だから対話的、Chain型だから自律的」でもない。人の関与をどこに挟むかは、アーキテクチャとは独立した判断です。

スクリプトを必須にするか、オプションにするか

判断基準は一つ。「LLMがゼロからできるか？」

  • 統計計算・並列処理・ファイル操作 → 必須スクリプト（LLMには任せられない）
  • 情報取得・フォーマット変換 → オプション（失敗してもLLMが自力で調べられる）

結局これは Agent Orchestration の話

ここまでのパターンは、Anthropic が2024年12月に整理したエージェント構成パターンとそのまま対応します。

パターン中身スキルでの対応
Prompt Chaining固定ステップの直列実行Skill Chain型
Routing入力を分類して振り分けdescription によるスキル選択そのもの
Parallelization同時実行して集約Sub-agent の並列生成
Orchestrator-Workers中央が動的に分解して委譲SKILL.md からサブエージェントへ
Evaluator-Optimizer生成と評価の反復skill-creator の改善ループ

スキルのファイル構造（SKILL.md / agents / scripts / references）は、これらのパターンを実装するための入れ物にすぎない、という見方ができます。

未解決の課題

スキル同士は Claude の注意（attention）を奪い合います。あるスキルの description を「押し強め」に最適化した結果、隣のスキルが呼ばれなくなる——ということは起こりえますが、それを検知する仕組みは今のところありません。個別最適だけでなく、スキル群全体の最適化が次の論点です。

04 / 応用

もっと大きく組むとき（Graph Engineering）

エージェントに長い仕事を任せると、判断も状態も副作用も1つのループに集中して、途中再開も監査も難しくなります。そこで出てきたのが Graph Engineering という言い方です。2026年7月ごろから広まりました。

要するに何をするのか

ループを捨てるのではなく、ループを「ノードの中」に閉じ込める。そして、ノードとノードの間を明示的な線でつなぐ。線には、通過条件・受け渡す状態・許される副作用・失敗時の扱いを持たせます。

  • ノード = 実行単位（LLMエージェント、普通の関数、評価器、そして人間の承認も同列に置ける）
  • エッジ = 単なる矢印ではなく契約。入出力の型、遷移条件、許可される副作用を含む
  • 状態 = 会話ログとは切り離した、スキーマ付きのデータ。途中保存（checkpoint）できる

こう組むと、独立した枝を並列に走らせる、途中で止めて人の承認を待つ、落ちても保存点から再開する、予算（トークン・時間・お金）を超えたら明示的な終了状態へ遷移する、といったことが設計として扱えるようになります。

ただし、飛びつく前に

この分野の一次資料は position paper（設計提案）が中心で、実装と実験結果が伴っていないものもあります。批判側の指摘も筋が通っています——ステートマシン、DAGスケジューラ、ワークフローエンジン、分散トレーシングは何十年も使われてきた技術で、graph という呼称は既存技術の言い換えでもある、と。

誤解しやすいところ

「グラフ化すれば信頼性が上がる」わけではない。誤った計画から誤った依存関係が作られると、明示グラフはその誤りを再現可能に、整然と実行します。複数エージェントは同じ誤情報にきれいに合意することもできる。テスト、外部の実測、人の判断といったグラフの外側の証拠を必ず置くこと。

「枝を増やせば速くなる」わけでもない。並列化はトークン、ツール呼び出し、レート制限、合流待ちを増やします。Anthropic の事例報告では、マルチエージェント構成は通常のチャットの約15倍のトークンを使いました（同社の特定構成での観測値であり、一般的な倍率ではありません）。

単純な方式から順に検討する

複雑さは足していくもの。次の順で、必要になった段階だけ上げていきます。

  1. 単一のプロンプト — 1回で終わり、副作用がなく、失敗しても安い
  2. 単一のエージェントループ — 手順が探索中に変わり、次の行動を事前に列挙できない
  3. 決定的なワークフロー — 手順と分岐が既知で、各ステップを機械的に検証できる
  4. 明示グラフ — 独立した枝、明示的な合流、人の承認ゲートがあり、経路自体を監査したい

「エージェントが複数いる」ことだけを graph 採用の理由にしない、というのが要点です。次の問いに「はい」が少ないなら、まだ単純な方式で足ります。

  • 独立して走らせられる枝が複数ある？
  • エージェント・関数・人の承認を、同じ実行の中で連携させる？
  • 数分を超える待ちや、プロセス再起動、後日の再開がある？
  • 支払い・削除・公開のように、権限の重さが違う副作用がある？
  • 途中の成果物と経路を、後から監査・再評価する必要がある？
Claude Code に引き寄せると

ハーネスの5層は、この文脈でいう「ノードを安全に動かすための土台」にあたります。CLAUDE.md と Rules がノード内部の判断材料、Skills がノードの中身、Agents がコンテキストの分離、Settings が権限ゲート。グラフを組む前に、まずこの土台を整えるほうが先です。

05 / 応用

外部サービスと繋ぐときの「認可疲れ」

GitHub、Slack、Notion、社内システム。エージェントに仕事を任せるなら連携させたくなりますが、そのたびに認可を求められる。「任せたと思ったら認可待ちで止まっていた」が起きます。

連携は3ステップに分解できる

  1. 認証 — 本人であることを社内IdPなどで証明する
  2. 認可の取得 — ツール（MCP）を使う許可をユーザーに求める ← ここが詰まる
  3. 実行 — ユーザーの代理としてツールを叩く

ステップ2の依頼が飛ぶのはツールを実行する瞬間なので、いつ来るか読めません。素朴な希望はこうです——SSOのように、最初の1回の認証で済ませられないか。

ブラウザが無い、という壁

SSOが成立するのは、IdP側にログイン済みセッションがあり、ブラウザがCookieでそれを持ち回れるから。ところがエージェントはブラウザを持っていないので、Cookieが使えません。手元にあるのは、認証の結果もらった id_token だけです。

しかも id_token は宛先（aud）がサービスごとに違い、自分宛でないトークンは受け取りを拒否するよう仕様で定められています。じゃあ無理か、というところで出てくるのが OBO（On-Behalf-Of）です。

OBO＝トークンの交換

手元の id_token を、外部サービスの認可サーバーに直接POSTして、そのサービス宛の access_token と交換してもらう。RFC 8693 で定義されたトークン交換のうち、「ユーザーの代理として認可を受ける」使い方をOBOと呼びます。

SSO（Cookie持ち越し）OBO（トークン交換）
提示するものセッションCookieid_token
提示先IdPの /authorize外部サービスの認可サーバーの /token
経路ブラウザのリダイレクト往復直接POST 1往復（リダイレクトなし）
ユーザーの関与なし（画面が出ない）なし

類似の方式に ID-JAG があります。IdPを一度経由する分、「どのエージェントがどの外部サービスに繋いでよいか」を会社全体で一元管理できるのが利点。ただし執筆時点ではIETF Draftで、IdP側の対応も必要です。

いちばん大事な設計：権限は絞られて出る

エージェント側のコードは1本で、要求するスコープも全員同じでかまいません。認可サーバー側で、そのユーザーが実際に持っている権限との「積」を取るのがポイントです。

営業担当のユーザーが発注ツールを叩こうとしても、交換後のトークンにその権限は入っていないので弾かれる。画面からログインしたときと同じ権限が、そのままエージェント経由にも適用される、という状態になります。

リスク中身対策
なりすまし盗んだ正規トークンを持ち込むクライアント認証で未登録・不一致を拒否
検証すり抜け偽造・期限切れ・別クライアント宛のトークン署名 / iss / exp を検証し、aud は事前登録と照合
権限昇格要求されたスコープをそのまま返す保有権限との積を取り、狭めたら応答で明示
宛先の鵜呑み要求された宛先をそのまま入れるaud はリソースサーバーに固定

ログに残すもの、絶対に残さないもの

監視すべきは3点。本人（誰の権限で）・代理人（どのエージェントが）・権限（何を許したか／何が足りなかったか）。これを認可サーバー側とMCPサーバー側の2箇所で記録します。

ただしJWTのクレーム名をそのまま使うのは避けます。同じ sub でも発行者が変われば値が変わるし、aud は交換の前後で宛先が移動するからです。「意味を固定した自前のフィールド名」に写し替えて記録すると、一貫して追跡できます。

残してはいけないもの

生のトークンと Authorization ヘッダ。ログに残ったトークンは、有効期限のあいだそのまま資格情報として使えてしまいます。出力の直前にレコードを走査して、JWTらしき文字列や client_secret が混ざっていたら出力自体を止める、という実装例もあります。

06 / まとめ

最初の一歩、この順で

全部を一度に整える必要はありません。小さく始めて、実際に起きた失敗を見てから足していくのが正攻法です。

  1. CLAUDE.md に「やらないこと」を3行書く。いちばん費用対効果が高い一手
  2. settings.json の deny に破壊的コマンドを並べる。allow は使いながら足していく
  3. 2回以上やった手順を Skill にする。その際、決定的な処理はスクリプトへ
  4. CLAUDE.md が膨らんできたら Rules に切り出す。常時要らないものは globs で条件付きに
  5. 大量に読むタスクが出てきたら Agent に委譲する。返すのは要約だけ
  6. deny で表せない動的な判断が要るときだけ Hooks。それまでは不要

迷ったときの3つの問い

  • これはLLMがゼロからできるか？ → できないならスクリプトへ
  • これは「お願い」で足りるか、「強制」が要るか？ → 取り返しがつかないなら deny か Hooks
  • この複雑さは、単純な方式より本当に良い結果を出しているか？ → 測ってから足す
通底している一つのこと

5層も、スキル設計も、グラフも、認可も、言っていることは同じです。その場のプロンプトで直すのをやめて、次も効く場所に書く。そしてAIに任せる範囲と、機械が決定的に守る範囲の境界を、自分の手で引くこと。
